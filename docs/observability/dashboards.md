# Docket observability dashboards

## Architecture and ownership

The DEV observability stack runs in the Terraform-owned `dev-observability` namespace. The `observability` Argo CD Application renders the official `prometheus-community/kube-prometheus-stack` Helm chart and the dashboard ConfigMaps in this repository. It is pinned to chart `89.2.1` (Prometheus `v3.14.0`, Prometheus Operator `v0.93.1`, Grafana `13.2.1`).

Prometheus scrapes Git-managed ServiceMonitors in namespaces labeled `environment=dev`. Grafana uses the chart-provisioned Prometheus datasource and its dashboard sidecar loads ConfigMaps labeled `grafana_dashboard: "1"`. Application repositories own the real runtime instrumentation; Kubernetes kubelet/cAdvisor and kube-state-metrics provide CPU, memory, restart, and availability data.

Grafana and Prometheus are `ClusterIP` services. They have no Ingress, Gateway route, HTTPRoute, or `LoadBalancer` Service and are not public.

## Monitored services

| Service | Metrics endpoint inside the cluster | ServiceMonitor | Dashboard | Application metrics |
| --- | --- | --- | --- | --- |
| frontend | `frontend.dev-frontend.svc.cluster.local:9090/metrics` | `frontend` | `Docket / frontend` | request count, HTTP errors, request-duration histogram |
| auth-api | `auth-api.dev-auth-api.svc.cluster.local:8000/metrics` | `auth-api` | `Docket / auth-api` | request count, HTTP errors, request-duration histogram |
| users-api | `users-api.dev-users-api.svc.cluster.local:8083/metrics` | `users-api` | `Docket / users-api` | request count, HTTP errors, request-duration histogram |
| todos-api | `todos-api.dev-todos-api.svc.cluster.local:8082/metrics` | `todos-api` | `Docket / todos-api` | request count, HTTP errors, request-duration histogram |
| log-message-processor | `log-message-processor.dev-log-message-processor.svc.cluster.local:9100/metrics` | `log-message-processor` | `Docket / log-message-processor` | processed messages, processing failures, processing-duration histogram |

The frontend metrics listener is deliberately separate from its public port 8080. The Gateway backend still references only port 8080, so port 9090 is cluster-internal. The worker's port 9100 is also exposed only by a `ClusterIP` Service.

Each HTTP dashboard shows requests per second, error rate, P50/P95 latency, CPU, memory, ready pods, and restarts. The worker dashboard replaces HTTP panels with message throughput, processing failures, and P50/P95 processing latency, while retaining the Kubernetes resource panels.

## Access Grafana

Confirm the service name, then start a local-only port-forward:

```bash
kubectl get svc -n dev-observability -l app.kubernetes.io/name=grafana
kubectl port-forward -n dev-observability svc/observability-grafana 3000:80
```

Open <http://localhost:3000>. The default username is `admin`. Retrieve the chart-generated password only in the local terminal; never place it in Git, chat, tickets, or shell history:

```bash
kubectl get secret observability-grafana -n dev-observability -o jsonpath='{.data.admin-password}' | base64 --decode
```

PowerShell equivalent:

```powershell
$encoded = kubectl get secret observability-grafana -n dev-observability -o jsonpath='{.data.admin-password}'
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($encoded))
Remove-Variable encoded
```

The password is generated by the Grafana Helm chart and is not stored in this repository.

## Verify Prometheus targets and data

List all monitors and forward the internal Prometheus service:

```bash
kubectl get servicemonitor -A
kubectl get svc -n dev-observability -l app.kubernetes.io/name=prometheus
kubectl port-forward -n dev-observability svc/observability-kube-prometheus-prometheus 9090:9090
```

Open <http://localhost:9090/targets> and verify all five Docket targets are `UP`. The API equivalent is:

```bash
curl -s http://localhost:9090/api/v1/targets
```

Generate a small amount of normal application traffic through the existing frontend, wait at least two 30-second scrape intervals, and run these representative queries in Prometheus:

```promql
sum by (service) (increase(docket_http_requests_total[10m]))
sum by (service) (increase(docket_http_request_duration_seconds_count[10m]))
sum(increase(docket_worker_messages_processed_total[10m]))
sum by (namespace) (rate(container_cpu_usage_seconds_total{namespace=~"dev-(frontend|auth-api|users-api|todos-api|log-message-processor)",container!="",container!="POD"}[5m]))
sum by (namespace) (container_memory_working_set_bytes{namespace=~"dev-(frontend|auth-api|users-api|todos-api|log-message-processor)",container!="",container!="POD"})
```

Do not mark real-data validation complete unless the application counters and latency histograms are present and non-zero for at least three services; CPU/memory data alone is insufficient.

## Troubleshoot an empty dashboard

1. Confirm the application Deployment uses the CI-published instrumentation image tag; never invent a tag or deploy one manually.
2. Check the Pod, Service endpoint, and monitor: `kubectl get pods,svc,endpoints,servicemonitor -n <namespace>`.
3. Confirm the Service has the expected `app` label and the ServiceMonitor endpoint uses the named `http` or `metrics` port.
4. Inspect <http://localhost:9090/targets> for the exact scrape error.
5. Query `up`, then the raw metric name, before debugging Grafana.
6. Confirm the Grafana datasource is named `Prometheus` with UID `prometheus` and the dashboard ConfigMaps have `grafana_dashboard: "1"`.
7. Use a time range containing recent traffic and wait at least 60 seconds after rollout.

## Persistence and capacity

Prometheus and Grafana persistence is intentionally disabled until a compatible live StorageClass is verified. Prometheus uses ephemeral storage, so historical samples can be lost when its Pod is replaced. Dashboards and the datasource are provisioned from Git and return automatically after Pod replacement. Before merging the stack, the platform operator must confirm the configured requests fit on the two DEV nodes with `kubectl top nodes` and `kubectl top pods -A`; capacity must not be expanded without a separate reviewed decision.

## Extending observability

- Alerts: add reviewed `PrometheusRule` resources in Git and route notifications through a separately approved Alertmanager configuration; never configure final alerts only in a UI.
- Tracing: deploy a Git-managed tracing backend and OpenTelemetry Collector, then connect the applications' existing tracing paths without exposing the backend publicly.
- Business metrics: add low-cardinality counters/histograms in the owning application repository, add tests, publish an immutable image through CI, then add the corresponding ServiceMonitor/dashboard or alert through GitOps. Never use user IDs, emails, tokens, raw URLs, or request bodies as labels.
